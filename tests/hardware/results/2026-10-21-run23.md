## Cause of the stuck thread

The crash report includes the stuck thread:

```
svcWaitProcessWideKeyAtomic / condvarWaitTimeout / SDL_CondWait   SDL_syscond.c:146
decode_thread                                                      Ren'Py ffmedia.c
SDL_RunThread / RunThread                                          SDL_thread.c:292
```

It is waiting for a stop signal (`media_close`) that never comes. Ren'Py's own shutdown does
this, in order:
1. `audio.quit()` (`renpy/audio/audio.py:1173`) stops the periodic thread. That thread is the
   only caller of `renpysound.periodic()`.
2. It fades the channels out with `fadeout(0)`.
3. `RPS_quit` (`renpysound_core.c:1373`) stops the channels.

`RPS_quit` never drains the `dying` list (`renpysound_core.c:1434`), which holds streams that
finished in the audio callback. A stream that ends during steps 1–3 is therefore never closed,
and its decode thread waits forever. Waiting longer cannot help, which is why the 3 s wait
did not.

## Fixes (runtime `2f70a173…`, not yet run on a Switch)

- `rsl_bridge.py` adds a `config.python_exit_callbacks` entry. It runs after `audio.quit()` and
  calls `renpysound.periodic()` once more, so the `dying` streams are closed while Python still
  runs. On the desktop SDK the callback runs ("finished audio streams closed at exit") and the
  scenario still passes 26/26.
- The close-the-software path shows the system error dialog (`errorApplicationShow`) instead
  of the libnx console.
