# Hardware run 20 — 2026-10-20: non-ASCII file names on the SD card

Runtime `b4174981…` (self-test splits the non-ASCII case out of the filesystem check).
Application mode, handheld. The loader was not changed.

Evidence:
- `cache/python-selftest.txt`, fetched over FTP;
- FTP uploads from the Mac through sphaira's server: 6 single names, then a sweep of 188
  names (all hiragana and katakana, plus 漢字中文한글éüß and an emoji).

| Test | Actual | Status |
|---|---|---|
| Self-test, filesystem (ASCII) | Write, fsync, rename, read back, list, remove | PASS |
| Self-test, non-ASCII names | `café.txt`, `ブ.txt` in NFD, folder `フォルダ`: created. `セーブ.txt`: `ENOENT`. `os.listdir` of the folder: `[]`. fs encoding utf-8, UTF-8 mode on | FAIL |
| FTP upload of the same kind of names | Same split, through a different program (sphaira) | FAIL |

## Finding

A name can be created exactly when its UTF-8 bytes also form well-formed Shift-JIS (CP932 lead
byte 0x81–0x9F or 0xE0–0xFC followed by a trail byte 0x40–0x7E or 0x80–0xFC). That rule
predicts all 193 results, for example:
- `セーブ.txt` fails: the last byte of `ブ`, 0x96, is a lead byte followed by `.`;
- `글.txt` and the emoji succeed.

- [Certain] libnx passes names through unchanged (`fsdev_convertfromfspath` is a byte copy),
  and the runtime and sphaira both show the same behaviour. So the Shift-JIS parsing happens
  below libnx: [Likely] Horizon's FS service.
- [Certain] Directory listings leave out every non-ASCII entry, even ones that were created.
  This is true for both our runtime and the FTP server. Those files still open by their exact
  name.
- Not tested: names written by a PC through a card reader.

Consequence: a game whose loose files have non-ASCII names cannot be installed reliably, and
Ren'Py would not see those files when it scans `game/`. The test folders were removed afterwards.
