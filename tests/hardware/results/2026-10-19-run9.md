## Cause of the crash: SDL's timer thread outlives the runtime

The crash report lists one module, `renpy-loader` at `0x7a7eccf000`. The crashing thread's
PC and return addresses are all near `0x203e…`–`0x203f…`, outside the loader. They fit the
run 8 runtime `.nro` loaded at `0x203e3a7000`:
- the PC is the instruction after `svc 0x1C` (`svcWaitProcessWideKeyAtomic`);
- all 9 LR and return addresses follow a call.

The offsets were named by matching code bytes in the `dist/` runtime ELF:

```
PC    svcWaitProcessWideKeyAtomic+0x4
LR    condvarWaitTimeout+0x2c
RA00  __syscall_cond_wait+0xc
RA01  sem_timedwait+0x68
RA02  (no unique match; between sem_timedwait and SDL_TimerThread)
RA03  SDL_TimerThread+0x1c4
RA04  SDL_RunThread+0x34
RA05  RunThread+0xc
RA06  __thread_entry+0x44
RA07  _EntryWrap+0xa8
```

`X0 = 0xEA01` is the kernel's "timed out" result. So SDL's timer thread was waiting with a
timeout. The runtime returned to the loader, and hbloader replaced the runtime's code with
the loader's. When the wait expired, the thread returned into code that no longer existed.

The thread survived because of how SDL counts its timer subsystem:
- `runtime.log` shows the SDL shutdown mask `0x4030` (audio, video, events), with no timer bit.
- `SDL_AddTimer` starts the timer thread on demand, but does not count the timer subsystem
  as initialised.
- Without that count, `SDL_QuitSubSystem` and `SDL_Quit` never call `SDL_TimerQuit`, which
  is what joins the thread.

Ren'Py starts the timer with `pygame.time.set_timer(PERIODIC, …)` (`renpy/display/core.py`).

## Fix for run 10 (runtime `fed4dc1b…`, pushed and verified over FTP; loader still `b6997861…`)

- `quit_sdl()` (`runtime/main.c`) now calls `SDL_InitSubSystem(SDL_INIT_TIMER)` before
  reading `SDL_WasInit`.
- This takes a reference on the running timer, so the shutdown loop quits it and
  `SDL_TimerQuit` joins the thread.
- The build has 0 warnings, and the disassembly shows the call before `SDL_WasInit`.
- The build also carries the run 9 runtime changes from run 8 (memory log, applet-mode
  image cache cap).
- To check on the console:
  - `runtime.log` shows `SDL shutdown: subsystems 0x4031` and `SDL shutdown: timer`;
  - the loader stays up for more than a minute after the return.
- Rollback copy of the run 8 runtime: `build-test/renpy-runtime-run8-1dce359e.nro` (not in git).

## Run 10 (same day, runtime `fed4dc1b…`): timer fix works; Exit then crashes sphaira

- **PASS:** `runtime.log` shows `SDL shutdown: subsystems 0x4031` and `SDL shutdown: timer`.
  The loader then stayed up 76 s on its menu with no crash.
- **FAIL:** "Exit to Homebrew Menu" → sphaira crashed at start-up.
  - Crash report `01792348033_0100cd801ce5e000.log`: 2168-0002, Data Abort at
    `0x2b0dd13000` (page-aligned), PC `sphaira+0x2ea6c4`.
  - One module (sphaira) and one thread.
  - Exiting from a loader session that did not run a game (01:16) did not crash.

[Likely] cause: thread stacks that CPython's threads leave mapped.
- CPython 3.12.8 detaches every thread it creates (`Python/thread_pthread.h:301`,
  `pthread_detach`).
- In this libnx, `pthread_detach` only returns ENOSYS (88); there is no
  `__syscall_thread_detach`. Only `pthread_join` calls `threadClose`.
- So when a Python thread exits, its stack stays mapped. libnx maps a stack with
  `svcMapMemory`, which leaves the heap pages behind it borrowed and inaccessible.
- The loader's heap audit shows 8548 KiB borrowed at a fresh start and 9472 KiB after a game.
  That is 924 KiB more, exactly 7 stacks of `0x21000` (132 KiB; the same size as the SDL
  timer thread's stack in the run 9 report).
- The next program in the process gets those pages back from its allocator and faults on
  first use. sphaira's Data Abort on a page boundary fits this, but the address was not
  checked against the borrowed ranges.
- This would also explain the run 7 crash in `malloc` on relaunch.

Workaround until fixed: after playing, close the software from the HOME menu instead of
"Exit to Homebrew Menu". That ends the process, and with it the leaked mappings.

## Fix for run 11 (runtime `35508472…`, pushed and verified over FTP; loader still `b6997861…`)

- `runtime/main.c` defines `__syscall_thread_detach`, newlib's hook behind
  `pthread_detach`. It records the thread and closes earlier detached threads that have
  exited.
- At exit (`close_detached_threads`, before the heap audit), every exited thread is closed.
  That unmaps its stack and frees its handle.
- The build has 0 warnings. `pthread_detach` now branches to the hook where it had a `nop`.
- To check on the console:
  - `runtime.log` shows `detached threads: N closed, 0 still running`;
  - `borrowed` at loader start is back near 8548 KiB;
  - Exit to the Homebrew Menu after a game does not crash.
- Rollback copy of the timer-fix runtime: `build-test/renpy-runtime-run10-fed4dc1b.nro`.
